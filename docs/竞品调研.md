# 竞品调研：让单个应用走代理，而不开 TUN

调研时间：2026-11-13 · 调研方式：DeepWiki 逐个核实源码与文档，不凭项目名推测

## 一句话结论

市面上把「某个应用」送进代理的成熟方案只有两大类，**都绕不开「要 TUN」或「要改应用的启动方式/注入库」**；
「让应用用它自己认的方式去连本地代理」这一条路没有成熟开源实现，tunless 走的是这个空位。

## 为什么会有这个工具

典型的冲突场景：

- 某些客户端（Cursor、Antigravity、Codex、各类 CLI Agent）不读 macOS 系统代理，**不开 TUN 就连不上外网**。
- 但 TUN 会**接管全部流量**，把内网域名（`*.17usoft.com`、`*.elong.com`）也劫持走，
  结果是开了 TUN 就上不了内网，关了就上不了外网。

所以真正需要的不是「更全局的代理」，而是「**只让这几个应用走代理，其余原样**」。

## 四类现有方案

| 方案 | 拦截手段 | 要 TUN | 要 root | macOS | 只影响指定 app | 代表项目 |
|---|---|---|---|---|---|---|
| 库注入 | `LD_PRELOAD` / `DYLD_INSERT_LIBRARIES` 钩 `connect()` | 否 | 否 | 是 | 是 | proxychains-ng |
| 系统调用追踪 | `ptrace` 改写 `connect()` 目的地 | 否 | 否 | **否** | 是 | graftcp |
| 防火墙重定向 | iptables/pf 重定向 + `SO_ORIGINAL_DST` | 否 | **是** | **未支持** | 靠 UID/GID | redsocks |
| 虚拟网卡 | TUN + 用户态协议栈 | **是** | 是 | 是 | `process_name` 只是匹配条件 | mihomo / sing-box / clash-verge-rev |

### 1. proxychains-ng（库注入派）

- 启动器给目标进程设 `LD_PRELOAD`（Linux）或 `DYLD_INSERT_LIBRARIES` + `DYLD_FORCE_FLAT_NAMESPACE`（macOS），
  动态库钩住 libc 的 `connect()`，把 TCP 连接改送到代理。
- 子进程通过 `fork()` 继承进程状态；`execvp()` 派生的新程序同样受 `LD_PRELOAD` 影响。
- 只处理 TCP；UDP/ICMP 不管。
- README 自己承认的短板：脚本、大量派生进程的程序、大量 `dlopen()` 的程序可能不可靠；
  macOS 上 **SIP 会阻止注入系统应用**；Go 这类静态链接程序根本不经过 libc。
- 对我们最有价值的启发：**「注入成功」不等于「流量被接管」**，必须验证。

### 2. graftcp（ptrace 派）

- 用 `ptrace(2)` 跟踪目标，记录 `connect(2)` 的原始目的地，把地址换成本机一个 token 端口，
  内部监听器再按 token 还原目的地、经 SOCKS5/HTTP 代理出去。
- 支持 fork/clone 的子进程，还会清掉 `CLONE_UNTRACED` 防止子进程逃逸。
- **明确只支持 Linux**：README 说明 macOS 的 `ptrace(2)` 缺少所需能力，Makefile 直接拒绝非 Linux 构建。
- 对我们的意义：这是一条 macOS 上走不通的路，不用再考虑。

### 3. redsocks（防火墙重定向派）

- 不自己装规则，需要你用 iptables（或 pf）把匹配的 TCP 流量重定向到它的监听端口，
  再用 `SO_ORIGINAL_DST` 拿回原始目的地。
- 需要 root 起服务；可以按 UID/GID 做「哪些进程走代理」，属于间接的 per-app。
- **macOS 未支持**：代码里有 `USE_PF`，但 Makefile 只在 OpenBSD 启用；README 说作者没有 macOS 机器可测。

### 4. TUN 派（mihomo / sing-box / clash-verge-rev）

- 通过虚拟网卡接管系统流量，再用规则分流。这是目前最"万能"的方案，也是大家最终都退回 TUN 的原因。
- **clash-verge-rev**：只有「系统代理 / PAC / TUN」三个开关，**没有任何按应用选择的能力**
  （DeepWiki 核实：系统代理走 PAC 或全局指向混合端口，TUN 靠路由表排除，排除的是网段不是应用）。
- **sing-box**：有 `process_name` 路由规则，容易误以为能按 app 选。但它只是
  「流量进来之后按进程名匹配」的**条件**，不负责把流量抓进来；系统代理模式下只有认代理的 app 才会进来，
  所以想覆盖陌生 app 依然要 TUN。
- 结论：TUN 是"抓流量"和"选应用"两件事被绑死的地方，而这正好和「内网不能被劫持」冲突。

## tunless 的位置

现有方案的二分法：

```
要 TUN        -> 能抓所有流量，但会劫持内网          （mihomo / sing-box / clash-verge）
改注入/追踪    -> 能只抓一个进程，但 macOS 上限制多、且不适用静态链接程序
```

tunless 走的是第三条：

```
让应用用它自己认的方式，去连一个本地代理
```

具体到每个应用，就是读它自己的配置（`settings.json` 的 `http.proxy`、`~/.codex/.env` 的 `HTTP_PROXY`）、
注入环境变量、必要时重启它。本地转发服务（`127.0.0.1:8899`）再按域名分流：
内网域名直连内网 DNS，公网域名交给上游 mihomo。

这条路的代价是**必须一个应用一个应用地适配**，没有通用解；收益是**不需要 root、不需要 TUN、不动系统路由**。

## 为什么这块没有成熟开源项目

调研下来，原因很直接：

1. **每个应用的"认代理"方式都不一样。** Antigravity 的模型流量在 `language_server`（Go，认 `HTTPS_PROXY`）；
   Cursor 的 Agent 走独立传输层，只认 `settings.json`，3.28 之前 HTTP/2 还完全绕过代理；
   Codex 读 `~/.codex/.env` 且**优先级高于进程环境变量**；桌面客户端还要重启才生效。
   这些差异没有任何通用抽象能吞掉。
2. **"配置了"不等于"生效了"。** 环境变量会被 app 自己的配置文件覆盖（Codex 的 `.env` 就是活例子），
   客户端把配置读进内存后不重启就还是旧值。必须实测。
3. **通用方案已经存在（TUN），所以没人愿意做逐个适配。** 只有遇到"TUN 会破坏内网"这种硬约束，
   才有动力走这条路。

## 借鉴与取舍

### 要保留的

- **验证优先于信任**（来自 proxychains 的教训）：不假设"写了配置就生效"。
  tunless 现在的做法是读真实连接（`lsof` 看进程实际连到哪个代理端口），
  比"注入后假定成功"更硬。**每个适配器都应该以这一步收尾。**
- **子进程意识**（来自 graftcp）：GUI app 会派生大量 helper，
  Cursor 的 Agent 单独一条网络通路、Codex 的 `app-server` 才是真正发请求的进程。
  判断"客户端走没走代理"必须看真正负责网络的子进程，不能只看主进程。

### 可以考虑的补充：通用注入兜底

`DYLD_INSERT_LIBRARIES` 在 macOS 上对**非 SIP 保护**的应用是可行的，可以做一档兜底，
覆盖还没适配的应用。但必须清楚它的边界：

- Electron 的 GPU / renderer 子进程可能绕过；
- Go 静态链接程序（如 `language_server`）不经过 libc，注入无效；
- SIP 保护的系统二进制无法注入。

所以它只能当兜底，**不能替代按应用适配的适配器**。

### 明确不做的

- 不接管系统路由（那是 TUN 的地盘，也正是本工具要避开的）。
- 不要求 root。
- 不通过防火墙规则做重定向（macOS 上未验证，且需要 root）。

## 附：调研记录（DeepWiki 原始结论摘要）

- `rofl0r/proxychains-ng`：`LD_PRELOAD` / `DYLD_INSERT_LIBRARIES` 钩 `connect()`；macOS 支持但 SIP 会阻注入；仅 TCP；脚本/多进程/`dlopen` 场景易失效。
- `hmgle/graftcp`：`ptrace` 改 `connect()` 目的地；支持 fork/clone；**仅 Linux**，README 明确 macOS 不支持（`ptrace` 能力不足）。
- `darkk/redsocks`：防火墙重定向 + `SO_ORIGINAL_DST`；需 root；`USE_PF` 仅 OpenBSD，**macOS 未支持**。
- `clash-verge-rev/clash-verge-rev`：只有系统代理 / PAC / TUN；**无 per-app 选择**；TUN 的排除是网段而非应用。
- `SagerNet/sing-box`：`process_name` 是路由匹配**条件**，不是捕获手段；系统代理模式只覆盖认代理的 app。
- `xjasonlyu/tun2socks`、`heiher/hev-socks5-tunnel`：都需要 TUN；排除项按网段配置，不是按应用。
- `sst/opencode`：只有自用的环境变量代理，没有跨应用的 per-app 代理能力。
